# Literature Review & Codebase Audit: Exact N-Queens Algorithms for $N \le 12$

## 1. Executive Summary & Benchmark Regime ($N \le 12$ in WebAssembly)

This review synthesizes exact N-Queens algorithms from the computer science and operations research literature (retrieved via OpenAlex and alphaXiv/arXiv) and maps them directly to the C++17/WebAssembly benchmark suite in this repository. Local builds compile solvers with Emscripten (`em++ -O2 -std=c++17`) to `wasm32` (`-sSTACK_SIZE=1048576`, `-sALLOW_MEMORY_GROWTH=1`, `-sMAXIMUM_MEMORY=512MB`, single-threaded, exceptions disabled; `driver/scripts/build-solvers.mjs`), while the judging VM may compile with Emscripten's default **64 KB `STACK_SIZE`** (where `-O2` disables stack-overflow assertions so overflows fail silently). Solvers are evaluated across four **full-enumeration** problem contracts (`Tester/Harness/nqueens.h`, `Tester/Harness/nqueen_runtime.cpp`) up to **$\max N = 12$** (`Tester/Board/preplaced.ts`):

| Problem Variant | Function Signature | Rule Semantics | Theoretical Complexity | Output Scale at $N = 12$ |
| :--- | :--- | :--- | :--- | :--- |
| **Normal** | `solveNQueens(int n)` | Place $N$ non-attacking queens on empty $N \times N$ board; return every solution (`vector<int>` of length $N$). | Decision: $O(N)$ / trivial; Counting: `#P`-open (asymptotically $((1\pm o(1))ne^{-\alpha})^n$, $1.94 < \alpha < 1.9449$; [Simkin 2023, p. 1](https://www.alphaxiv.org/pdf/2107.13460?page=1)) | $Q(12) = 14{,}200$ solutions ($1{,}787$ fundamental $D_4$ orbits) |
| **Pre-placed** ($n$-Queens Completion) | `solvePreplaced(int n, const vector<pair<int,int>>& preplaced)` | Keep $P \in [0, N-1]$ locked queens; return every complete valid $N$-queen board. | **NP-complete** and **`#P`-complete** ([Gent et al. 2017, Theorem 37, p. 836](https://doi.org/10.1613/jair.5512)) | $0$ to $14{,}200$ ($P = 0$); sharply drops as $P$ rises |
| **Holes** (Blocked $n$-Queens) | `solveHoles(int n, const vector<string>& grid)` | Forbid queens on `'H'` cells; attacks **pass through** holes; return every $N$-queen board. | **NP-complete** and **`#P`-complete** ([Gent et al. 2017, Corollary 38, p. 837](https://doi.org/10.1613/jair.5512)) | $0$ (unsolvable typed boards) up to $14{,}200$ ($H = 0$) |
| **Walled** (Queens Separated by Pawns) | `solveWalled(int n, const vector<string>& grid)` | Forbid queens on `'W'` walls; walls **stop attacks** along rows, columns, and diagonals; return every **maximum-cardinality** board (`vector<pair<int,int>>`). | **NP-complete** (via Planar 3-SAT; [Martin 2007, p. 1–2](https://www.alphaxiv.org/pdf/cs/0701049?page=1)); max cardinality $\le \lceil N/2 \rceil^2$ ([Chatham 2016, p. 97](https://doi.org/10.1515/rmm-2016-0010)) | Up to $36$ queens per board at $N=12$; output count highly variable (Cartesian product across components) |

### Why $N \le 12$ Is a Distinct Algorithmic Regime

At $N \le 12$, every complete backtracking algorithm (other than unpruned $N!$ permutation generation, where $12! = 479{,}001{,}600$) finishes in microseconds to tens of milliseconds. Consequently, asymptotic branching reductions matter **only if their per-node constant factor does not outweigh the search tree size**, and two harness-specific measurement realities dominate both optimization tracks:

1. **CPU-Fastest Track (`min` of 7 timed runs in `Tester/Execution/measure.ts`)**: Because `solveNQueens(12)` visits as few as ~25k–50k nodes under $D_4$ canonical pruning yet must construct and return **14,200 `std::vector<int>` objects**, heap allocation and vector-copy overhead during solution materialization can exceed the entire search cost. At $N \le 12$, register-resident bitwise transitions (`x & -x`, portable C++20 `<bit>` `std::countr_zero` / `std::popcount`), exact-capacity output reservation, and zero-overhead loop unrolling routinely beat heavier constraint propagators (CDCL SAT, CP `all-different`, pointer-chasing DLX) that shine at $N \ge 20$.
2. **Memory-Lightest Track (`.data`/`.bss` + `sbrk(0)` delta under a 64 KB stack budget)**: While the local harness reads dynamic heap via `nq_heap_top()` (`sbrk(0)` delta across `nq_solve()`), the judging leaderboard counts **static/global memory (`.data` + `.bss`) in addition to dynamic heap**, and the judging VM may use Emscripten's default **64 KB `STACK_SIZE`** (with `-O2` disabling overflow checks so stack overflow silently corrupts linear memory). Because Emscripten's `sbrk` never returns freed memory to the host, **every transient heap allocation, `std::vector` geometric growth reallocation, NRVO-defeating copy, or `static`/global scratch array permanently raises the reported memory score**. Therefore, solvers must keep `.data`/`.bss` at **0 extra bytes** (forbidding global variables and `static` scratch buffers) and enforce a **fixed compile-time stack ceiling (~32 KB total live stack frame footprint)** without non-standard stack-probing headers. For `Normal` at $N=12$, the irreducible output floor for `std::vector<std::vector<int>>` in `wasm32` is roughly:
   - Outer vector buffer: $14{,}200 \times 12\text{ B} \approx 170.4\text{ KB}$ (if reserved exactly once; up to $2\times$ higher with geometric doubling).
   - Inner buffers: $14{,}200 \times (12 \times 4\text{ B} + 8\text{ B dlmalloc chunk header}) \approx 795.2\text{ KB}$.
   - **Total irreducible output floor**: $\approx 966\text{ KB}$ ($\sim 0.94\text{ MB}$). Any solver that eliminates `.data`/`.bss` scratch arrays, stays within a fixed compile-time stack ceiling (~32 KB, e.g., `uint64_t stackSols[4096]`, falling back to a single exact-sized heap allocation only when dense $N = 12$ boards exceed $4{,}096$ solutions), calls exact `solutions.reserve(total)`, and preserves C++17/C++20 NRVO approaches this lower bound without risking silent stack overflow.

### Official Competition Rules (`Syarat Kode Program` & `Peraturan Umum`) & Evaluation Cadence

All candidate implementations for both tracks must strictly obey five binding code rules and match the official judging workload:

- **Rule 1 (No Custom Allocator Overrides)**: Overriding `operator new`, `operator delete`, `malloc`, or `free` is prohibited. All heap reduction must come from standard C++ container discipline (NRVO, exact `reserve()`, and minimal transient heap usage).
- **Rule 2 (No `#line` Directives)**: Preprocessor `#line` directives are banned.
- **Rule 3 (Strict File-Scope Discipline)**: File scope may contain **only** constants, `struct`/`class` definitions, and functions—**no global variables** (and no function-local `static` scratch buffers, keeping `.data`/`.bss` overhead at 0 bytes).
- **Rule 4 (Headers & Portable Standard Intrinsics Only)**: Solvers may include **only** C++ Standard Library headers (e.g., `<bit>`, `<cstdint>`, `<array>`, `<vector>`, `<algorithm>`) and `"nqueens.h"`. Non-standard Emscripten headers (such as `<emscripten/stack.h>` for `emscripten_stack_get_free()`) and compiler-specific SIMD headers (`<immintrin.h>`, `<wasm_simd128.h>`) are strictly disallowed. Use portable C++20 `<bit>` (`std::countr_zero`, `std::popcount`) and standard integer types *(note: local `driver/scripts/build-solvers.mjs` currently passes `-std=c++17`, so verify `-std=c++20` support on the judge or guard with `#if __cplusplus >= 202002L` using standard C++ bit ops without non-standard headers)*.
- **Rule 5 (No Pre-Computed Placements)**: Pre-computed full or partial queen-placement lookup tables—including hardcoded 1-row or 2-row symmetry seeds, partial board tables, or precomputed $D_4$ orbit tables—are prohibited. All $D_4$ fundamental orbits, border pruning masks, and coordinate transforms must be computed dynamically at runtime inside `nq_solve()`.
- **Test Distribution, Cutoff, & Submission Cadence**:
  - **90 total test cases** across $N = 4 \dots 12$: **9 Normal** test cases (1 per $N$), plus **27 test cases each** for **Pre-placed**, **Holes**, and **Walled** (3 board configurations per $N$ spanning sparse, medium, and dense constraint regimes).
  - **Timeout**: **15 s** hard per-test cutoff (matching `cutoffSeconds` in `Tester/Configuration/tester.config.json`).
  - **Submission budget**: **2 submissions per problem case per day**, making comprehensive local verification mandatory before every submission (exact solution-count checks, duplicate detection, sparse-to-dense stress tests across $N = 4 \dots 12$, and 64 KB stack verification).

## 2. Track 1: CPU-Fastest Algorithms for $N \le 12$

### 2.1 Bitwise / Bitboard Backtracking (Richards / Somers Pattern)

#### Mechanism
Pioneered in software by Martin Richards (1997, cited in [Gent et al. 2017, p. 838](https://doi.org/10.1613/jair.5512)) and Jeff Somers (2002, cited in [Preußer et al. 2009/2012, p. 2](https://openalex.org/W3199396099) and [Yao & Li 2025, p. 1, 3](https://www.alphaxiv.org/pdf/2511.12009?page=1)), bitboard backtracking compresses the entire conflict state of row $r$ into three machine-word bitmasks: occupied columns `col`, down-left diagonals `d1`, and down-right diagonals `d2`. As [Yao & Li (2025, p. 3)](https://www.alphaxiv.org/pdf/2511.12009?page=3) summarize:
> "The algorithm utilizes three 32-bit variables (`cur`, `left`, and `right`) to encode the occupied states of columns, diagonals, and anti-diagonals respectively... As for finding the valid positions in the next row, we only need to compute the bitwise OR of `cur`, `left`, and `right`, and then take the bitwise NOT to obtain all valid positions."

Candidate columns are iterated without scanning blocked squares using two's-complement lowest-set-bit extraction:
```cpp
uint32_t avail = rowAllowed & ~(col | d1 | d2);
while (avail) {
  uint32_t bit = avail & -avail;   // isolate LSB
  avail ^= bit;                    // clear LSB (or avail &= avail - 1)
  // recurse with (col | bit), ((d1 | bit) << 1), ((d2 | bit) >> 1)
}
```
When full solution boards must be materialized (rather than merely counted), column index $c$ is recovered in a single WASM `i32.ctz` instruction via portable C++20 `std::countr_zero(bit)` from `<bit>` (existing `-std=c++17` repository solvers currently call `__builtin_ctz(bit)`; SIMD headers such as `<immintrin.h>` and `<wasm_simd128.h>` are disallowed under Rule 4).

#### Asymptotic & Constant-Factor Analysis at $N \le 12$
- **Nodes visited (unconstrained, no symmetry)**: Identical to row-by-row backtracking ($2{,}057$ nodes at $N=8$, $35{,}539$ nodes at $N=10$, $\sim 856{,}188$ internal placements at $N=12$).
- **Constant-factor speedup**: [Lam et al. (2026)](https://doi.org/10.52714/dthu.ns.3283.2031) report that bitmask backtracking visits the exact same tree as array backtracking while achieving $2.75\times$ speedup at $N=8$ and $4.14\times$ at $N=10$. On modern CPUs, [Gent et al. (2017, p. 841)](https://doi.org/10.1613/jair.5512) measured their Richards-style C++ bitboard solver at "$\approx 42$ million nodes being searched per second in a single thread," noting that it "searches exceptionally fast per search state although the intelligence of the search process is limited" (p. 838).
- **Lookahead caveat**: [Preußer et al. (2009/2012, p. 6–7)](https://openalex.org/W3199396099) showed that partial solutions peak sharply around depth $L = N - 4$, where $>90\%$ of partial boards are uncompletable. Yet projecting blocking vectors onto 1 or 2 future columns yielded only a "rather disappointing level of 3–4 percent for each individual conflict model" (p. 7), because the added per-node check overhead nearly cancels the pruned subtrees in software.
- **Last-row / last-two-rows unrolling**: By contrast, terminating recursion 1–2 rows early avoids the widest tree layers with minimal instructions. [Yao & Li (2025, p. 6–7)](https://www.alphaxiv.org/pdf/2511.12009?page=7) show that evaluating row $N-1$ directly at row $N-2$ without pushing a stack frame yields **$>25\%$ end-to-end speedup**, provided conditionals are fused (`if (valid_pos == 0 || ...)` rather than two sequential branches).

#### Constrained Variants & Enumeration Mode
- **Pre-placed**: [Gent et al. (2017, p. 838)](https://doi.org/10.1613/jair.5512) adapt Richards's shift-bitmask algorithm by skipping rows with locked queens and injecting diagonal attacks of pre-placed queens during shifts (or, as in `Solver/preplaced/preplaced-bitmask-mrv.cpp`, pre-baking fixed-queen attacks into `rowAllowed[i]` and using variable shift gaps `<< gap[i]` / `>> gap[i]`). For $P = 1$, gap-shift bitmask DFS beats dynamic MRV; for $P \ge 2$, fixed row order can thrash if a tightly constrained row sits near the bottom.
- **Holes**: Trivial $O(1)$ per-row mask (`avail = rowAllowed[r] & ~(col | d1 | d2)`), as noted by [Gent et al. (2017, p. 838)](https://doi.org/10.1613/jair.5512). Optimal for sparse holes ($H \ll N^2/5$), especially when oriented along the tightest of the 4 board directions; degrades near the Blocked $n$-Queens phase transition where dynamic ordering wins.
- **Walled**: **Not directly applicable**, because walls break the global diagonal invariants $r \pm c = \text{const}$ and allow $>1$ queen per row/column.
- **Single-solution vs. Full-enumeration**: For unconstrained single-solution $N$-Queens, constructive $O(N)$ patterns or gradient local search ([Sosič & Gu 1990](https://doi.org/10.1145/101340.101343)) find one solution instantaneously (even for $N = 500{,}000$). For **full enumeration** at $N \le 12$, bitboard DFS (combined with $D_4$ symmetry) is the undisputed CPU-fastest foundation for Normal and sparse Pre-placed/Holes.

### 2.2 Symmetry Breaking ($D_4$ Dihedral Canonical Pruning) & Dynamic Variable Ordering (MRV / Fail-First)

#### Mechanism: Dihedral $D_4$ Symmetry Breaking
The square chessboard has symmetry group $D_4$ of order 8 (4 rotations, 4 reflections). As proven by [Preußer et al. (2009/2012, Appendix A, p. i–iii)](https://openalex.org/W3199396099) (see also [Bell & Stevens 2009](https://doi.org/10.1016/j.disc.2007.12.043)):
- For $N > 1$, **no valid solution is reflection-self-symmetric**, because every reflection axis is itself a queen attack line (row, column, or main/anti-diagonal), so at most one queen can lie on it and any off-axis queen would attack its mirror image.
- Only rotational self-symmetries exist: $180^\circ$ self-symmetric boards have orbit size $4$ (count $w$), $90^\circ$ self-symmetric boards have orbit size $2$ (count $v$, impossible whenever $N \equiv 2, 3 \pmod 4$), and asymmetric boards have orbit size $8$ (count $s$). Thus $S = 8s + 4w + 2v$, giving $1{,}787$ fundamental solutions for $Q(12) = 14{,}200$ (almost an exact $8\times$ search reduction!).

There are three levels of symmetry exploitation in the literature:
1. **2-fold mirror symmetry**: Restrict row 0 to columns $0 \dots \lfloor (N-1)/2 \rfloor$ (and if $N$ is odd and `cols[0] == N/2`, restrict row 1 to the left half; [Yao & Li 2025, p. 1](https://www.alphaxiv.org/pdf/2511.12009?page=1), [Preußer et al. 2009/2012, p. i](https://openalex.org/W3199396099)). Cuts the search tree by $2\times$ with zero per-node overhead. In full enumeration, emitting both `cols` and its L/R mirror `N - 1 - cols[r]` requires zero deduplication (since no solution is mirror-self-symmetric for $N > 1$!).
2. **8-fold $D_4$ canonical border pruning**: Partition solutions into (a) corner-queen boards (rotated to $(0,0)$, breaking the remaining main-diagonal transpose symmetry via `cols[1]` bounds and leaf comparison `cols <= transpose(cols)`), and (b) non-corner boards (rotating/reflecting the minimum corner-distance border queen $c_0$ to $(0, c_0)$ with $1 \le c_0 \le \lfloor (N-2)/2 \rfloor$ and forbidding closer placements on the left, right, and bottom borders). This cuts the search tree by nearly **$8\times$** using only runtime-generated local per-row bitmasks `rowMask[r]`, with canonicality/orbit checks needed **only at leaves** where another border queen ties $c_0$. *(Rule 5 compliance: all $D_4$ border masks, fundamental orbits, and transformed coordinates must be computed dynamically at runtime inside `nq_solve()`—never via pre-computed 1-row/2-row symmetry seed tables or partial placement lookups.)*
3. **Dynamic Symmetry Breaking During Search (SBDS)**: Introduced by [Gent & Smith (2000)](https://openalex.org/W41784264) (and formalized taxonomically in [Cohen et al. 2006](https://doi.org/10.1007/s10601-006-8059-8)), SBDS posts symmetric nogoods upon backtracking so symmetry breaking never conflicts with dynamic variable/value ordering heuristics (such as MRV). While vital for general CSPs, SBDS carries constraint-posting overhead that is excessive for $N \le 12$ compared to static bitmask border canonicalization.

#### Mechanism: Dynamic Variable Ordering (MRV / Fail-First) & Forward Checking
[Haralick & Elliott (1980)](https://doi.org/10.1016/0004-3702(80)90051-x) established the **fail-first principle** (Minimum Remaining Values, MRV) combined with **Forward Checking (FC)** on $N$-Queens: at each step, filter domains of unassigned variables and branch on the variable with fewest legal values (immediately backtracking on domain wipeout).
- **Critical insight at $N \le 12$**: Static sequential row order (`row = 0..N-1`) visits more nodes than MRV, **but** computing domain sizes across all remaining rows at every node costs $O(N)$ bitmask operations (or $O(N^2)$ if done via array scans!).
- On **unconstrained Normal $N \le 12$**, pure shift-bitmask DFS with $D_4$ pruning is **faster** than MRV because $D_4$ already shrinks the tree $\sim 8\times$ and every inner node executes only ~5 bitwise ALU instructions.
- On **constrained Pre-placed ($P \ge 2$) and dense Holes**, MRV + forward checking + unit propagation (forced row / hidden-single column) dramatically outperforms fixed-order DFS, because pre-placed queens and dense holes create severely unbalanced row/column domains (often inducing immediate domain wipeout or unit chains). Using shiftable global diagonal masks `diagSum` (bit $r+c$) and `diagDiff` (bit $c-r+N-1$), row $r$'s legal domain is computed in **$O(1)$** via `rowAllowed[r] & ~(colMask | (diagSum >> r) | (diagDiff >> (m - r)))`, eliminating Haralick & Elliott's state-copying overhead that [Knuth (2000, p. 23)](https://www.alphaxiv.org/pdf/cs/0011047?page=23) specifically criticized!

#### Constrained Variants & Enumeration Mode
- **Pre-placed & Holes**: Any asymmetric placement of pre-placed queens or holes **destroys $D_4$ symmetry** (unless the input itself is checked for residual automorphisms, which rarely hold for random instances). Conversely, MRV + forward checking + unit propagation is **ideal** for both variants (and seamlessly handles $P=0$ / $H=0$ via fast-path dispatch to $D_4$ bitmask search). Note that for Holes, an $O(N^2)$ bitmask Kuhn bipartite matching pre-check immediately rejects boards failing Hall's marriage condition before search starts.
- **Walled**: $D_4$ symmetry breaks under arbitrary wall placements; MRV translates into selecting the smallest active segment or minimum-branching-set vertex cover in the conflict graph (Section 2.5).
- **Single-solution vs. Full-enumeration**: In single-solution mode, $D_4$ symmetry is mostly irrelevant for Normal, while MRV + fail-first + value-ordering (least-constraining value) dramatically speeds up finding a first solution on hard Blocked/Completion instances. In full-enumeration mode on Normal, **naive symmetry breaking that expands and sorts/deduplicates all 8 images can actually be slower than no symmetry breaking** (verified empirically in `Solver/normal/backtracking-symmetry.cpp`, ~23 ms vs ~19 ms for plain bitmask at $N=12$), whereas **canonical border pruning with direct orbit expansion** (`d4-symmetry-bitmask.cpp`) avoids sorting entirely and wins decisively.

### 2.3 Knuth's Algorithm X, Dancing Links (DLX), and Bitwise Exact Cover

#### Mechanism
[Knuth (2000, p. 20–21)](https://www.alphaxiv.org/pdf/cs/0011047?page=20) formulates $N$-Queens as a **generalized exact cover** instance:
- **$2N$ primary columns**: $R_0, \dots, R_{N-1}$ (ranks) and $F_0, \dots, F_{N-1}$ (files), each covered **exactly once**.
- **$4N - 6$ secondary columns**: $A_1, \dots, A_{2N-3}$ (sum-diagonals $r+c$) and $B_1, \dots, B_{2N-3}$ (diff-diagonals $N-1-r+c$), each covered **at most once** (the 4 length-1 corner diagonals $A_0, A_{2N-2}, B_0, B_{2N-2}$ occur in only one row and are omitted; p. 20). Secondary headers are **not** linked into the root header ring; their `L` and `R` pointers self-loop so column selection only inspects primary columns (p. 19).
- **$N^2$ matrix rows**: Row $(r, c)$ has four `1`s in $\{R_r, F_c, A_{r+c}, B_{N-1-r+c}\}$.

Algorithm X branches **bidirectionally** on whichever primary column (rank **or** file!) has the smallest current size $S[c]$ (Golomb–Baumert / S-heuristic). Knuth implements the reversible cover/uncover dance via circular quadruply-linked lists (`L, R, U, D, C` per data node; plus `S, N` per column header; p. 5) using the identity:
$$L[R[x]] \leftarrow L[x],\; R[L[x]] \leftarrow R[x] \quad \text{undone by} \quad L[R[x]] \leftarrow x,\; R[L[x]] \leftarrow x.$$
Crucially, [Knuth (2000, p. 21–22)](https://www.alphaxiv.org/pdf/cs/0011047?page=21) discovered two decisive optimizations for $N$-Queens exact cover:
1. **Bidirectional row+column branching vs. row-only branching**: Allowing Algorithm X to branch on files as well as ranks shrinks the $N=12$ tree from **312,729 R-nodes (5,173,071 R-updates)** down to **211,716 nodes (3,594,752 updates)** — a **$32.3\%$ node reduction** (Table on p. 22).
2. **Organ-pipe tie-breaking order**: Linking primary headers from the center outward ($R_{\lfloor N/2\rfloor}, F_{\lfloor N/2\rfloor}, R_{\lfloor N/2\rfloor-1}, F_{\lfloor N/2\rfloor-1}, \dots, R_0, F_0$) breaks MRV ties in favor of central lines, which attack the most cells. At $N=16$, sequential order $R_0 \dots R_{15} F_0 \dots F_{15}$ needed 312.5M nodes and 5.80B updates, whereas organ-pipe order required only **54% as many updates** (193.0M nodes, 3.13B updates; p. 22).

#### Constant-Factor Comparison: Pointer DLX vs. Bitwise Exact Cover at $N \le 12$
Despite DLX's strong node reduction, [Knuth (2000, p. 10–11, 22)](https://www.alphaxiv.org/pdf/cs/0011047?page=10) candidly reports its high per-node constant factor:
- Each link update executes **~14 memory accesses** when maintaining `S[c]` (vs. ~8 without `S`; p. 10). At $N=12$, 3,594,752 updates translate to **$\sim 50.3$ million scattered memory accesses**!
- Comparing DLX against Dana Scott & Hale Trotter's bitwise pentomino solver on MANIAC, Knuth observes: *"From this standpoint the technique of dancing links is actually a step backward from Scott's 40-year-old method, although of course that method works only for very special types of exact cover problems in which simple geometric structure can be exploited."* (p. 11) and concludes that *"On small cases it is nearly as fast as algorithms that have been tuned to solve particular classes of problems... On large cases it appears to run even faster than those special-purpose algorithms, because of its ordering heuristic."* (p. 22–23).

**Bitwise & 64-bit SWAR Exact Cover** (implemented in `Solver/holes/holes-swar-d4-algx.cpp`, superseding the original `holes-bitmask-algx.cpp`) resolves this exact trade-off for $N \le 12$: it executes **Knuth's exact bidirectional row+column Algorithm X search tree** (including column forward checking, forced-row / hidden-single-column unit propagation, and Knuth organ-pipe central tie-breaking), **without building or mutating a linked-list matrix**. By packing all $N \le 12$ row domains (12 bits per row, 4 rows per 64-bit word with `0x7000` sentinels) into three 64-bit registers (`d0, d1, d2`, specialized to two words for $N \le 8$) alongside a 1-multiply SWAR column-row gather (`((v * 0x0001000200040008ULL) >> 48)`) and portable C++20 `<bit>` / ISO C++17 bit operations, dead-row, forced-row, count-2-row, and `(once, twice, thrice)` column-cardinality checks execute across all 12 rows in parallel with zero inner loops. Per-node cost drops from ~238 scattered memory accesses (17 updates/node $\times$ 14 accesses in DLX at $N=12$) to a few dozen register-resident ALU ops.

*(Note on ZDD-accelerated DLX: [Nishino et al. 2017](https://doi.org/10.1609/aaai.v31i1.10662) accelerate DLX on large exact-cover instances by memoizing subproblem states into a Zero-suppressed Binary Decision Diagram (ZDD). While asymptotically powerful for counting or structured large instances, constructing hash-table ZDD caches and then decompressing them into 14,200 explicit `std::vector<int>`s adds severe heap and constant-factor overhead at $N \le 12$.)*

#### Constrained Variants & Enumeration Mode
- **Pre-placed**: Cover the $P$ pre-placed cell rows upfront (or fix their bits in bitwise Algorithm X); works naturally and exploits bidirectional row/column MRV.
- **Holes**: Simply omit the matrix row $(r, c)$ for every hole `'H'` (or clear bit $c$ in `rowAllowed[r]` and bit $r$ in `colAllowed[c]`). **Bitwise Algorithm X is the top algorithmic family for moderate-to-dense Holes at $N \le 12$**, combining exact bidirectional pruning with register speed.
- **Walled**: **Poor fit** — walls allow zero or multiple queens per row/column, turning exact cover (`= 1`) into maximum independent set (`<= 1` per line segment while maximizing total chosen rows), which Algorithm X cannot bound tightly without an optimization objective.
- **Single-solution vs. Full-enumeration**: DLX / Bitwise Algorithm X excels at both, particularly for proving UNSAT on hard Blocked $n$-Queens instances where fixed-order DFS explores massive dead subtrees.

### 2.4 Cache-Friendly Iterative / Loop-Unrolled DFS

#### Mechanism
Converting recursive bitmask DFS into an iterative loop over a tiny explicit stack array eliminates function call/return overhead, parameter spills, and WASM call-stack frame management. In [Yao & Li (2025, Algorithm 2, p. 4)](https://www.alphaxiv.org/pdf/2511.12009?page=4), each stack level stores just four 32-bit integers (`cur`, `left`, `right`, `valid_pos` = 16 bytes/level; for $N \le 12$ with last-two-rows unrolling, max stack depth is $N - 2 \le 10$, requiring at most **160 bytes** — fitting in 3 L1 cache lines!). Furthermore, keeping the active level's `(col, d1, d2, avail)` in local scalar registers and only pushing/popping on downward/upward transitions minimizes memory traffic.

#### Constant-Factor Analysis at $N \le 12$ (WASM `-O2` Nuance)
- **Recursion vs. Iteration on `wasm32`**: On `wasm32` compiled with `em++ -O2`, a small recursive function (`dfs(row, col, d1, d2)` with depth $\le 10$) passes all four arguments in WASM locals (which V8 Liftoff/TurboFan maps to CPU registers) and saves minimal frame state, whereas an explicit array stack requires indexed loads/stores into linear memory (`stack[top]`), which carry bounds-check/base-offset overhead in WASM.
- **When iterative/unrolled DFS wins**:
  1. **Unrolling the bottom 2–3 rows** (`row == n - 2`, or even `row == n - 3` inlined inside the loop) eliminates $>85\%$ of recursive call instructions without paying linear-memory stack load/store costs on every node!
  2. **Explicit iterative stack without bitmasks** (as currently written in `Solver/normal/backtracking-iterative.cpp`, which uses `std::vector<Frame>` on heap + byte-array loops) is **strictly slower** than recursive bitmask DFS. To beat recursive bitmask DFS, an iterative DFS MUST pair a fixed stack array (`uint32_t stack[12][4]`) with register-cached top-of-stack variables and bitwise transitions.

### 2.5 Exact Maximum Independent Set / Clique Algorithms for the Walled Variant

Because Walled N-Queens is NP-complete ([Martin 2007](https://www.alphaxiv.org/pdf/cs/0701049?page=1)) and asks for **every maximum-cardinality independent set** of the wall-segmented attack graph $G = (V, E)$ (equivalently, every maximum clique of its complement $\bar{G}$), standard $N$-Queens solvers fail. For $N \le 12$, $|V| \le 144$, which fits cleanly in **3 `uint64_t` words** (192 bits).

Three key findings from the Maximum Clique literature directly govern CPU performance on Walled boards:
1. **Bit-Parallel Set Representation (BBMC)**: [San Segundo, Rodríguez-Losada, & Jiménez (2011)](https://doi.org/10.1016/j.cor.2010.07.019) replaced adjacency lists / integer arrays in Tomita's MCQ/MCS with bitstrings (`N[v]` and `invN[v]`), computing candidate intersections (`newP = P & N[v]`) and colour-class greedy independent sets (`Q &= invN[v]`) in $O(|V|/64)$ bitwise ops (just 1–3 CPU instructions at $N \le 12$!). [Prosser (2012, Table 2 & Section 5, p. 26, 36)](https://www.alphaxiv.org/pdf/1207.4616?page=26) confirmed that BBMC explores the exact same search tree as MCSa while running **"typically twice as fast"** on DIMACS and random graphs (up to $6.94\times$ on `MANN-a45`), and noted that replacing boxed objects with raw bit-word arrays amplifies this speedup further.
2. **Colour Repair / 1-Vertex Recoloring Trade-off (MCS / BBMCI / BBMCX)**: [Tomita et al. (2013, Section 4.1, p. 1288–1289)](https://doi.org/10.1587/transinf.e96.d.1286) introduced `Re-NUMBER` ($O(|R|^3)$ worst-case), moving a vertex $q$ out of colour class $C_{k_1}$ into $C_{k_2}$ so a vertex $p$ exceeding the pruning threshold $No_{\text{th}} = |Q_{\max}| - |Q|$ can be absorbed below the threshold and pruned; [San Segundo et al. (2013)](https://doi.org/10.1007/s11590-011-0431-y) ported this to bitstrings (`BB_ReCol`). Crucially, [Prosser (2012, Section 4.1, p. 22, 36)](https://www.alphaxiv.org/pdf/1207.4616?page=22) found that on smaller/moderate graphs ($n = 100$), **"MCSb1 is always slower than MCSa1, i.e. the colour repair is too expensive and when $n = 100$ MCSb1 is often more expensive to run than MCQ!"** — meaning recoloring should be gated or applied selectively when branching sets remain large!
3. **Static Vertex Ordering & Geometric Bounds**: Both [Tomita et al. (2013, p. 1289)](https://doi.org/10.1587/transinf.e96.d.1286) and [Prosser (2012, Section 4.3, p. 26–29)](https://www.alphaxiv.org/pdf/1207.4616?page=26) demonstrate that reconstructing the adjacency bitmatrix once in static vertex order improves cache locality and preserves coloring quality. Specifically, Prosser found **minimum-width (degeneracy) ordering (style 2)** consistently visits fewer nodes than plain degree ordering for BBMC/MCSa. Furthermore, on Walled boards, every wall-delimited row segment and column segment is a known geometric clique in $G$ (an independent set in $\bar{G}$), providing $O(\#\text{segments})$ upper bounds and pigeonhole branching covers before even running general greedy coloring (as exploited in `Solver/walled/walled-bbmcx-clique.cpp`). Note also one critical difference from standard Maximum Clique papers: **all maximum-size solutions must be returned**, so pruning uses strict inequality (`curSize + bound < bestSize`, **never** `<=`).

## 3. Track 2: Memory-Lightest Algorithms for $N \le 12$

### 3.1 Judging-Harness Memory Model & Competition Rules (`.data`/`.bss` + `sbrk(0)` + 64 KB Stack)

Under the leaderboard judging harness, measured memory includes **both static/global segments (`.data`/`.bss`) and dynamic heap (`sbrk(0)` delta)**, while the judging VM may compile with Emscripten's default **64 KB `STACK_SIZE`** (rather than the local repo's 1 MB `-sSTACK_SIZE=1048576`). Because `-O2` strips Emscripten's stack-overflow assertions, exceeding 64 KB of stack silently corrupts WASM linear memory instead of trapping cleanly.

Combined with the competition's `Syarat Kode Program` (Rules 1–5), this imposes four hard engineering constraints on every memory-track solver:
1. **Zero `static`/global variables & no allocator overrides (Rules 1–3)**: Overriding `operator new`/`delete` or `malloc`/`free` is banned (Rule 1), `#line` directives are banned (Rule 2), and file scope may contain **only** constants, `struct`/`class` definitions, and functions—**no global variables** (Rule 3). Never declare `static` or file-scope scratch buffers, lookup arrays, or solver structs; keep `.data`/`.bss` overhead at **0 extra bytes**, with all scratch storage allocated as local automatic variables inside `nq_solve()`.
2. **Standard C++ headers only & fixed compile-time stack ceiling (~32 KB) (Rule 4)**: Only C++ Standard Library headers (`<bit>`, `<cstdint>`, `<array>`, `<vector>`, `<algorithm>`) and `"nqueens.h"` are permitted. Non-standard Emscripten headers (`<emscripten/stack.h>` / `emscripten_stack_get_free()`) and compiler-specific SIMD headers (`<immintrin.h>`, `<wasm_simd128.h>`) are strictly forbidden. Therefore, solvers **cannot probe free stack at runtime** and must instead enforce a **fixed compile-time ceiling of ~32 KB total live stack frame footprint** (e.g., `uint64_t stackSols[4096]` = 32 KB, leaving ~32 KB headroom for recursion frames, local temporaries, and runtime calls under a 64 KB stack).
3. **No pre-computed placements (Rule 5)**: Hardcoded full or partial queen-placement tables (including 1-row/2-row symmetry seeds or precomputed $D_4$ orbit tables) are disallowed; all $D_4$ orbits, border masks, and coordinates must be generated dynamically at runtime inside `nq_solve()`.
4. **Portable bit operations (Rule 4)**: Use C++20 `<bit>` (`std::countr_zero`, `std::popcount`) and standard fixed-width integer types rather than compiler-specific intrinsics or SIMD headers.

Total reported memory then decomposes into **Static/Global Scratch** ($M_{\text{static}} = 0$ by rule), **Auxiliary Heap** ($M_{\text{aux}}$), and **Output Container Heap** ($M_{\text{out}}$):

| :--- | :--- | :--- | :--- |

### 3.2 Compact Exact-Cover Structures: Array-Indexed DLX vs. XOR-Linked DLX (XDLX)

Two literature approaches aim to compress Knuth's quadruply-linked DLX matrix:

1. **XOR-Linked Dancing Links (XDLX)**: [Varalakshmi et al. (2023, p. 90–94)](https://doi.org/10.17762/ijritcc.v11i1.6054) replace the four directional pointers `L, R, U, D` with two XOR-difference pointers `H(x) = L(x) ^ R(x)` and `V(x) = U(x) ^ D(x)`, plus boundary arrays `rows[m]`, `last_in_row[m]`, and `vlast[n]`. For dense matrices of size $m \times n$, they reduce link pointers from $2mn$ to $mn + 2m + n + 1$ ($\approx 50\%$ reduction; Table I, p. 94).
   - **Critical audit for $N \le 12$**: Inspecting their `Cover` and `UnCover` pseudocode ([Varalakshmi et al. 2023, p. 92–93](https://doi.org/10.17762/ijritcc.v11i1.6054)) reveals **two fatal flaws for our benchmark**:
     - For sparse $N$-Queens ($4$ ones per row out of $6N-6$ columns), the auxiliary arrays `rows[N^2]`, `last_in_row[N^2]`, and `vlast[6N]` add $2N^2 + 6N$ pointers on top of $2 \times 4N^2 = 8N^2$ XOR links, shrinking the real saving from $50\%$ to only $\sim 35\%$.
     - Worse, because an XOR node cannot locate its neighbors without knowing one adjacent address, `Cover` and `UnCover` execute **linear scans** (`while(current != c)`, `while(V(rowcurrent) != Xor_diff)`, and linear `get_vlast_of_c(c)`), destroying DLX's $O(1)$ unlink/relink invariant!
2. **Local Array-Indexed Arena DLX**: [Hardin (2023, Section 6.1, p. 166–167)](https://www.alphaxiv.org/pdf/2311.08862?page=6) demonstrates implementing Knuth's Dancing Links inside a fixed-capacity array `nodeArr` using compact integer indices rather than heap-allocated pointers. On `wasm32`, for $N \le 12$ where node count $\le 645 < 65{,}535$, placing a `uint16_t`-indexed arena as a **local stack struct inside `solveNQueens`/`solveHoles`** (never `static`/global, which would count against `.bss`) shrinks each node (`L, R, U, D, C, row`) to **12 bytes** ($7.7$ KB total — safely inside a 64 KB stack, **0 B heap**, **0 B `.bss`**, full $O(1)$ cover/uncover, and better spatial locality than XDLX!). Yet for $N$-Queens specifically, **Bitwise Algorithm X beats even 12-byte local-arena DLX in both memory ($\sim 250$ B vs. $7.7$ KB) and speed**.

### 3.3 Output Allocation Hygiene & 64 KB-Safe Buffering: The True Bottleneck at $N \le 12$

A crucial finding of our codebase audit is that **for full enumeration at $N = 12$, auxiliary search memory is dwarfed by the output container `std::vector<std::vector<int>>`**. Under the judging harness (counting `.data`/`.bss` + `sbrk(0)` with a potential 64 KB stack), memory minimization prioritizes **output allocation hygiene first**, followed by **64 KB-safe local stack buffering**:

1. **Priority 1 — Eliminate Member-Return NRVO Bugs (`return solutions;`, never `return search.solutions;`)**: Returning a struct member vector disables C++17 Named Return Value Optimization and triggers a full deep copy of all 14,200 inner vectors, **doubling `sbrk` heap peak** (~1 MB wasted at $N=12$). Already logged as a project gotcha in `.projectmem/summary.md`, this bug is STILL present in 5 baseline solvers under `Solver/normal/` (`backtracking-bitmask.cpp`, `backtracking-naive.cpp`, `backtracking-iterative.cpp`, `backtracking-mrv.cpp`, `dlx-exact-cover.cpp`) — fixing it via local return or `std::move` is the single largest memory win.
2. **Priority 2 — Exact `solutions.reserve(total)` to Eliminate $2\times$ Geometric `std::vector` Growth**: Calling `solutions.push_back(cols)` dynamically during DFS triggers ~14–15 geometric outer-vector reallocations interleaved with inner `std::vector<int>` allocations, leaving dead holes in Emscripten's `dlmalloc` heap and inflating `sbrk` by up to ~170 KB–340 KB. Buffering compact solutions first and calling `solutions.reserve(total)` **exactly once** before constructing inner vectors eliminates all outer-vector reallocation waste.
3. **Priority 3 — Fixed Compile-Time ~32 KB Local Stack Buffering with Single Exact-Sized Heap Fallback**: Never allocate a 128 KB stack buffer (`uint64_t[16384]`), which silently overflows Emscripten's default 64 KB stack under `-O2`; never use `<emscripten/stack.h>` / `emscripten_stack_get_free()` (banned by Rule 4); and never move buffers into global or `static` storage (banned by Rule 3 and penalized in `.bss`). Instead:
   - Enforce a **fixed compile-time ceiling (~32 KB total live stack frame footprint)** using only standard C++ headers (`<array>`, `<cstdint>`, `<vector>`, `<bit>`, `<algorithm>`) and `"nqueens.h"`—specifically `uint64_t stackSols[4096]` (4-bit packed board representation: $4 \times 12 = 48$ bits per board $\implies 8$ bytes/board $\times 4{,}096 = 32\text{ KB}$ local stack, leaving ~32 KB headroom for DFS frames and runtime).
   - **Coverage**: A 4,096-entry local stack buffer covers **100% of $N \le 11$ instances** on the stack with zero heap spill ($Q(11) = 2{,}680 \le 4{,}096$) and covers all constrained $N = 12$ instances with $\le 4{,}096$ solutions. For Normal $N = 12$ under $D_4$ symmetry, packing the dynamically computed $1{,}787$ fundamental orbits as parallel local arrays (`uint64_t cols[2048]` + `uint8_t mask[2048]` = **18 KB**, cutting `d4-symmetry-bitmask.cpp`'s current 34.8 KB `Fundamental[2048]` nearly in half!) fits comfortably inside the 64 KB stack with **zero heap spill**!
   - **Single exact-sized heap fallback for dense $N = 12$ ($> 4{,}096$ solutions)**: When a sparse Pre-placed or Holes $N = 12$ board exceeds $4{,}096$ solutions, avoid geometric doubling of `heapSols`—instead allocate a **single exact-sized (or exact upper-bound `Q(12) - 4096 = 10,104` $\times 8\text{ B} \approx 80.8\text{ KB}$, or two-pass count-then-materialize) heap buffer** once, preventing fragmented `heapSols` growth before `solutions.reserve(total)`.
4. **Lookup Tables vs. Pure Bitwise Recomputation (Rule 5 Enforcement)**: [Preußer et al. (2009/2012, p. 7)](https://openalex.org/W3199396099) highlight that hardware/software designs trade state storage against recomputation: storing blocking history on a small local stack costs ~160 bytes and is faster than recomputing attacks from `cols[0..r-1]`. Under **Rule 5**, any **pre-computed full or partial queen-placement table** (including hardcoded 1-row/2-row symmetry seeds, partial board tables, or precomputed $D_4$ coordinates) is strictly forbidden; large lookup tables (e.g., ZDD memoization caches or `static`/global precomputed tables) also inflate `.data`/`.bss` or exhaust the 64 KB stack. At $N \le 12$:
   - **Compute tiny ($< 1$ KB) local-stack masks dynamically at runtime**: `rowAllowed[12]` (48 B), `colAllowed[12]` (48 B), `rowMask[12]` (48 B).
   - **Compute everything else on the fly via portable standard bit-ops**: diagonal shifts `(d1 | b) << 1`, `(diagSum >> r)`, `avail & -avail`, C++20 `<bit>` `std::countr_zero` / `std::popcount`, and dynamic $D_4$ coordinate transforms inside `nq_solve()` during materialization.
   - **Walled exception**: Runtime-built conflict/compatibility bitsets (`144 * 3 * 8 = 3.45 KB` each, $\approx 6.9$ KB total on local stack) are justified because wall-blocked ray walks cost $O(N)$ per pair and $7$ KB fits cleanly inside a 64 KB stack—**provided** recursive `expand()` does not stack-allocate multi-kilobyte `C[kMaxV]` arrays at every depth (which would blow through 64 KB!).

## 6. Synthesis: Recommended Optimization Roadmap (Both Tracks)

Without modifying code yet, the literature + codebase audit reveals clear, testable hypotheses for subsequent experiment branches:

1. **Immediate Zero-Risk Compliance & Output-Allocation Hygiene Fixes (Highest-Leverage Memory Wins)**:
   - **Fix member-return NRVO bugs** across all 5 affected baseline solvers (`backtracking-bitmask.cpp`, `backtracking-naive.cpp`, `backtracking-iterative.cpp`, `backtracking-mrv.cpp`, `dlx-exact-cover.cpp`) by returning a local `solutions` vector or `std::move` (cuts `sbrk` peak by $\sim 50\%$ immediately!).
   - **Enforce exact `solutions.reserve(total)`** wherever feasible to eliminate $2\times$ geometric outer-vector growth reallocations and `dlmalloc` fragmentation.
   - **Enforce Rules 1–5 across every solver**: zero global variables and zero `static` scratch buffers (file scope limited strictly to constants, types, and functions; Rule 3), no custom `operator new`/`delete` or `malloc`/`free` overrides (Rule 1), no `#line` directives (Rule 2), standard C++ headers (`<bit>`, `<cstdint>`, `<array>`, `<vector>`, `<algorithm>`) + `"nqueens.h"` only with zero Emscripten/SIMD headers (Rule 4), and zero pre-computed full/partial placement or 1-row/2-row symmetry seed tables (Rule 5).
   - In `dlx-exact-cover.cpp`, implement Knuth's organ-pipe primary ordering, unlink secondary headers from the root ring, drop the 4 trivial corner diagonals, and move the node pool into a **local stack `uint16_t` arena** ($\le 7.7$ KB — 0 B `.bss`, 0 B aux heap, safe under 64 KB stack).
2. **CPU-Fastest Track Hypotheses ($N \le 12$)**:
   - **Normal (9 official tests: $N = 4 \dots 12$)**: Benchmark `d4-symmetry-bitmask.cpp` with (a) 4-bit `uint64_t` fundamental packing (`uint64_t cols[2048]` + `uint8_t mask[2048]` = 18 KB local stack for tighter L1 locality and 64 KB stack safety, all orbits computed dynamically at runtime), (b) 3-row bottom unrolling / iterative fixed-stack inner loop, (c) portable C++20 `<bit>` (`std::countr_zero` / `std::popcount`), and (d) optimized `materialize()` construction (minimizing per-solution copy work within the mandatory `std::vector<std::vector<int>>` ABI).
   - **Pre-placed & Holes (27 official tests each: 3 sparse-to-dense configs per $N = 4 \dots 12$)**: Completed for Holes in `Solver/holes/holes-swar-d4-algx.cpp` (64-bit SWAR Bidirectional AlgX + 8-way $D_4$-orbit Holes search with verified `H <= N^2/8` crossover; see `Solver/docs/holes-optimization/holes-swar-d4-algx-report.md`). For Pre-placed, apply Knuth's **organ-pipe (center-first) tie-breaking**, bidirectional column branching for $P \ge 2$, and SWAR packing to `preplaced-bitmask-mrv.cpp`.
   - **Walled (27 official tests: 3 sparse-to-dense configs per $N = 4 \dots 12$)**: Benchmark `walled-bbmcx-clique.cpp` with (a) Prosser's **minimum-width (degeneracy) vertex ordering** vs. conflict-degree ordering, (b) **adaptive recoloring gating** (skipping `BB_ReCol` when candidate set size or unabsorbed count is small, per Prosser 2012), and (c) optional diagonal-segment clique cover checks.
3. **Memory-Lightest Track Hypotheses ($N \le 12$, Fixed ~32 KB Stack Ceiling & Zero `.data`/`.bss`)**:
   - **Fixed ~32 KB Local Stack Buffering + Exact-Sized/Zero-Aux-Heap Fallback**: Completed for Holes in `Solver/holes/holes-swar-d4-algx.cpp` (`3584`-entry packed `uint64_t` stack buffer + packed $D_4$ orbits achieving `0 B` auxiliary heap and `~35 KB` total stack across all 36 cases).
